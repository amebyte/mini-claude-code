核心机制 · CORE MECHANISM

先问「存在吗」，再决定「怎么说」

用 access 探测文件是否已存在：区分「覆盖 / 新建」不是逻辑分叉，而是为了返回文案——让用户和大模型知道这次到底发生了什么
write.ts — 最小核心实现
import { access, mkdir, writeFile } from 'node:fs/promises'; import { dirname, resolve } from 'node:path'; async function writeTool({ filePath, content }) { const abs = resolve(filePath); // ① 路径归一化 let existed = true; try { await access(abs); // ② 存在性探测 } catch { existed = false; // 抛异常 → 新建 } await mkdir(dirname(abs), { recursive: true }); // ③ 建齐父目录 await writeFile(abs, content, 'utf8'); // UTF-8 落盘 return existed ? `文件已成功更新：${abs}` // 覆盖 : `文件已成功创建于：${abs}`; // 新建 }
01
access() 存在性探测
没抛异常 → 已存在，记为「覆盖」；抛异常 → 不存在，记为「新建」。这道防线被完整保留。
02
mkdir(recursive) 建齐父目录
recursive: true 一次建齐所有缺失目录，写入前永远不用担心父目录不存在。
03
writeFile() UTF-8 落盘
根据 existed 返回「文件已成功更新」或「文件已成功创建于」——文案即状态。
[!]

真实源码还会做「写前必须 Read」校验、生成 diff 补丁、通知 LSP / VSCode。本小节只还原「路径归一化 + 存在性探测 + 写入」这条核心链路，但存在性探测这道防线被完整保留了。
