# 技术文章写作（Cobyte 风格）

## 概述

把任意一段代码 demo（Python/Node.js 等）改写为一篇结构完整、循序渐进、讲「原理」的 AI Agent 方向技术教程文章。风格基准来自 `D:\workspace\202608\md\reference` 目录下的 7 篇参考文章（作者：程序员 Cobyte）。

写作前先通读用户提供的 demo 代码，理解它「解决了什么问题、核心机制是什么、分几步实现」，再套用下面的模板与规范成文。

## 写作风格 DNA（务必内化）

这 7 篇文章共同的灵魂，用 6 句话概括：

1. **从底层讲原理，而非罗列步骤**——每篇文章都在回答「它到底是怎么工作的 / 本质是什么」。落点永远是「本质原理」「最小核心」「底层实现」，不是 API 说明书。
2. **先给问题，再给解法**——开头必有一个具体痛点或场景（如「只执行第一步就不动了」「无法跨语言调工具」），引出「为什么需要 X」，再进入实现。
3. **代码是主体，但每一段代码后都要用大白话解释**——代码块与自然语言交替推进，读者不用跑代码也能看懂。
4. **循序渐进，层层递进**——从最简单可用版本出发，指出它的瓶颈，再迭代升级（同步 → 异步 → 插件化；单工具 → 多工具 → 后台进程）。
5. **大量使用类比与设问**——用生活化比喻（USB-C 接口、说明书、门卫、人肉中转站、单兵作战 vs 协同系统）降低理解门槛，用「那么怎么实现呢？」推动阅读节奏。
6. **第一人称复数「我们」**——作者与读者是共同动手的伙伴，语气亲切、教学感强，绝不居高临下。

## 文章结构模板

标准骨架（编号用 `### 1.`、`### 2.`，子节用 `#### 4.1`、`#### 4.2`）：

```
# 标题

### 1. 前言
### 2. 为什么需要 X ？
### 3. 核心概念（一句话/一张图说清原理）
### 4. 代码实现
    #### 4.1 环境准备
    #### 4.2 工具定义
    #### 4.3 工具实现
    #### 4.4 核心逻辑
    ...（按 demo 的实际步骤拆分）
### 5. 测试 / 演示
### 6. 工作原理总结（可选）
### 7. 总结
```

**章节数量与命名可随主题伸缩**，但以下原则不变：
- 前言之后必有「为什么需要」或「回顾上一篇」。
- 实现部分必须拆成小节，每节一个代码块 + 一段解释。
- 结尾必有「总结」，提炼本质。

## 标题写法

参考文章的标题套路，任选其一（都要有「钩子」）：

| 套路 | 示例 |
| --- | --- |
| 数字 + 秘密/循环 + 破折号揭晓 | `30行代码，一个循环：这就是AI Agent的核心秘密—Agent Loop` |
| 面试官/场景设问 | `面试官：大模型是怎么调用工具的呢？` |
| X 本质原理：从…到… | `大模型 MCP 本质原理：从协议到代码实现` |
| X 接入/实现 Y 的实现原理 | `微信 ClawBot 接入本地 AI Agent 的实现原理` |
| 来，实现一个 X：从底层理解 Y | `来，实现一个 Mini Claude Code：从底层理解 AI Agent` |
| 深入理解 X 的实现原理 | `深入理解 subagent 的实现原理` |
| X 的本质原理 | `Agent Skills 系统的本质原理` |

要点：标题里出现「本质原理 / 实现原理 / 从底层理解 / 从…到…」这类字眼，是这套风格的强烈信号。

## 各章节写作规范

### 1. 前言
- 用一个**具体场景或小实验**切入（如「设计一个寻宝游戏」），或回顾上一篇文章的实现（「我们在上一篇文章中已经实现了…」）。
- 明确点出当前实现的**局限**（「只执行了第一步就不再执行了」），自然引出本文要解决的问题。
- 结尾用一句话抛出本文目标，可用设问收尾（「那么怎么实现呢？」）。
- 若文章是系列文，需引用/回看上一篇（「可以回看我的上一篇文章：《…》」）。

### 2. 为什么需要 X？
- 讲清「没有它之前世界是怎样的、有哪些痛点」。
- 对比「传统做法 vs 新做法」，突出新方案的价值。
- 常用句式：「为了让大模型…，OpenAI 提出了 **Function Calling** 机制」「而 X 正是为了解决这一问题应运而生：…」。

### 3. 核心概念
- 用**最精简的伪代码 + ASCII 流程图**先给读者一个全局印象，再展开细节。
- 示例（Agent Loop 的伪代码）：
  ```
  while 模型请求调用工具:
      执行工具调用
      将结果反馈给模型
  ```
- 配一张 ASCII 图表达数据流（输入 → 模型 → 工具 → 结果 → 回传模型）。

### 4. 代码实现
- **严格按 demo 的构建顺序**拆成小节，每小节标题是「动作/组件名」，如 `环境准备`、`工具定义`、`工具实现`、`核心循环`、`交互终端`。
- 每小节：一个代码块 → 一段 1–3 句的**大白话解释**（这段代码做了什么、关键点在哪）。
- 代码块内要有**中文行内注释**和 `# ---------- 工具定义 ----------` 式的**分段注释**。
- 复用前面已展示过的代码时，用 `# 省略...` 或 `// 省略...` 占位，不要重复贴整段。
- 迭代/新增代码时，用 `diff` 代码块（`+`/`-` 前缀）清晰展示「改了哪里」——这是这套风格的重要特征。

### 5. 测试 / 演示
- 给出**可复现的输入**（如要读取的文件内容、要执行的一句话指令）。
- 用 ` ``` ` 代码块展示**终端运行输出**（带 `$` 提示符），或插入运行截图（新文章用 `![image.png](...)` 占位）。
- 用一句话解读结果：「从结果可以看出…」「整个过程完全自主…」。

### 6. 工作原理总结（可选）
- 把整个流程压缩成**有序步骤列表**（1. 用户输入 → 2. 调用模型 → … → 回到步骤 2）。
- 点明「这就是 XX 的最小闭环 / 核心要义」。

### 7. 总结
- 先一句话收束本质（「所谓 X 模式本质就是…」）。
- 提炼 **3 个核心**或关键结论（可用加粗小标题 + 简短说明）。
- 附上**可扩展方向**（「在此基础上，你可以添加…」）。
- 末尾加**作者签名**（见下）。

## 代码呈现规范

- 语言标记：Python 用 ` ```py ` 或 ` ```python `，Node 用 ` ```js `，配置/数据用 ` ```json `、` ```xml `、` ```markdown `，改动用 ` ```diff `，纯文本/终端用 ` ``` `（不带语言）。
- 代码里使用 emoji 反馈结果：`✅` 成功、`❌` 失败、`🔧` 调用工具、`📁`/`📄` 文件、`🧩` 子任务、`🛠️` 工具、`🤔` 思考中、`👤`/`💬` 对话、`👀` 等待。
- 打印信息常用 ANSI 颜色（`\033[33m`、`\033[32m`、`\033[36m`），体现「终端交互」质感。
- 代码里的变量名、函数名、类名在正文中一律用**行内代码格式**（反引号）标注。
- 每个工具类的 `execute` 方法都要 `try/except`，错误信息以 `❌ …: {e}` 的形式作为正常返回值返回（让模型能感知错误）——这是这套代码风格的标志。

## 语言与修辞

- **口语化设问推动节奏**：「它是怎么做到的呢？」「那么怎么实现呢？」「有没有发现一个问题？」。
- **本质化表达**：高频使用「本质上就是 / 其实就是 / 简单来说 / 核心要义 / 最小闭环」。
- **生活化类比**：为抽象概念找一个实物/场景比喻，如 MCP = USB-C 接口、工具定义 = 说明书、路径校验 = 门卫、手动回填结果 = 人肉中转站、单 Agent = 单兵作战。
- **加粗关键名词**：首次出现的核心术语一律加粗（`**Agent Loop**`、`**Function Calling**`、`**subagent**`）。
- **系列文感**：频繁回看上一篇、预告下一篇，营造连载感。
- 行文使用中文，但代码、函数名、API 名保留英文。

## 图解与表格

- 协议字段、接口返回、参数说明用 **Markdown 表格**（字段 / 类型 / 必填 / 描述）。
- 架构与流程用 **ASCII 图**（`+---+` 框线或 `┌───┐` 方框 + 箭头）。
- 目录/层级结构用**缩进代码块**（`skills/ ├── …`）。

```

## 从 demo 到文章的工作流程

1. **读懂 demo**：确认它解决什么问题、核心机制是什么、代码分几个模块/步骤。
2. **提炼「本质」**：一句话说清它的底层原理（如「一个工具 + 一个循环 = 一个智能体」）。
3. **设计标题**：从标题套路表里选一种，把本质塞进钩子。
4. **搭骨架**：按结构模板列出章节与小节。
5. **拆解代码**：把 demo 按构建顺序切成若干「动作」，每段代码配一段解释。
6. **补前言与痛点**：设计一个能暴露「没有它会怎样」的具体场景。
7. **补测试演示**：给出输入、输出、解读。
8. **写总结**：提炼本质 + 3 个核心 + 扩展方向 + 签名。
